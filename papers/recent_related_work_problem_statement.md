# Repository-Level Structural Repair for LLM-Generated Code

## Problem statement

Code generated by large language models can be locally plausible yet inconsistent with the repository in which it must operate. It may reference missing symbols, misuse internal APIs, introduce undeclared dependencies, violate configuration or resource assumptions, break cross-file data contracts, contain invalid control flow, or omit required security guards. Such defects can pass local inspection and appear only during integration or execution. Existing work addresses parts of this problem—such as API hallucination, repository-aware context retrieval, multi-method bug repair, and security-aware patching—but does not provide a unified, evidence-grounded workflow for detecting and repairing diverse structural violations across files while preserving repository behavior. This project studies how repository structure and explicit project policies can guide repair candidates that are independently verified against static checks, compilation, and behavioral tests, with ambiguous or unsupported cases reported for human review rather than silently accepted.

## Approach statement

This project aims to mitigate and repair these errors by reusing knowledge already present in the repository—such as its symbols, APIs, dependencies, configuration, contracts, resources, control flow, and security policies. It will use computationally lightweight, deterministic techniques, including graph-based analysis and statistical ranking, to identify likely causes and generate repair candidates instead of relying on an LLM to perform the repair. Candidate fixes will be checked with static analysis, compilation, and behavioral tests; cases without sufficient evidence will be left for human review.

## Benchmarks used in related work

Four benchmarks or benchmark suites used by the papers above are relevant for evaluating repair or repository-level code tasks:

- **UnifiedFixEval** — introduced with StepwiseGraphFix for API-misuse repair, including repair tasks involving unseen libraries. [SANER 2026 paper](https://conf.researchr.org/details/saner-2026/saner-2026-papers/21/Progressively-Mitigating-API-Hallucination-in-LLM-Generated-Code-via-Knowledge-Graph-)
- **SWE-bench Lite and SWE-bench Verified** — repository-level issue-resolution benchmarks used to evaluate ExpeRepair. [FSE 2026 paper](https://conf.researchr.org/details/fse-2026/fse-2026-research-papers/147/ExpeRepair-Dual-Memory-Enhanced-LLM-based-Repository-Level-Program-Repair)
- **CoderEval and DevEval** — repository-level code-generation benchmarks used to evaluate RepoScope. [ICSE 2026 paper](https://conf.researchr.org/details/icse-2026/icse-2026-research-track/169/RepoScope-Leveraging-Call-Chain-Aware-Multi-View-Context-for-Repository-Level-Code-G)
- **Defects4J** — Java bug-repair benchmark used in the RepairAgent evaluation. [ICSE 2025 paper](https://conf.researchr.org/details/icse-2025/icse-2025-research-track/160/RepairAgent-An-Autonomous-LLM-Based-Agent-for-Program-Repair)

These benchmarks measure different tasks, so they are useful references rather than interchangeable measures of this project’s structural repair capability. Evaluation should include a benchmark aligned with repository-level structural violations and report repair verification (target violation removed, no new violations, compilation, and behavioral tests).

## Research gap and project positioning

Recent work demonstrates that graph representations can improve repository context, that API and package hallucinations are measurable and partially repairable, and that LLM agents can repair repository-level or multi-method bugs. The remaining opportunity is a unified repair process focused on **structural consistency across a repository**: normalize detection evidence, associate findings with likely root causes, construct bounded local or multi-file repair candidates, and accept a candidate only after repository-level checks and behavioral tests. Reweave/SCARF addresses this opportunity with a prototype for a documented subset of TypeScript, using existing repository graph views, explicit policy, isolated candidate verification, ranked alternatives, and abstention when evidence is insufficient.
